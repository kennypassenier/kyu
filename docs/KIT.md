# What kyu gets from chassis

> Generated by `chassis sync` from chassis 2.0.0. Do not edit
> by hand: the next `chassis sync --write` overwrites it. It describes the
> kit at that version; it matches this project as long as `chassis_tag` in
> `.chassis.toml` reads `v2.0.0`.

kyu is built on [chassis](https://github.com/kennypassenier/chassis-rs), a shared foundation
for small Rust web services. Everything below comes from the kit and works
the same way in every service built on it. What kyu does itself —
its routes, its pages, its own configuration — is described in the
project's own README and `docs/`.

**This binary is built with: core, dashboard, assets, self-update.** The kit can do
more than this document describes; what a feature this project does not
build would have added is left out here rather than explained as though it
were there.

## The door: how clients get in

Every request to a protected route carries a **client token**:

```bash
curl -sS -H 'Authorization: Bearer <client token>' \
     -H 'Content-Type: application/json' \
     -d '{}' http://127.0.0.1:8080/v1/…
```

A client token is issued per client, on the dashboard's **Clients** page
(a name, one click) or, for a service without a dashboard, with
`chassis clients` on the machine that runs it. The token is shown once and
can be revealed, copied, re-issued or revoked at any time; revoking locks
the client out the same second. A request without a valid token is
answered with HTTP 401 and a JSON body that says what to send.


Two secrets belong to the operator, not to clients, and live only in the
environment file (`/appdata/kyu/kyu-config/kyu.env`), never in a flag or a config file:

- `KYU_TOKEN` — the **admin token**: it logs you in on `/login`
  and also works as a bearer for scripts run by the operator.
- `KYU_SECRET_KEY` — the **secret key** (32 bytes, hex) that seals
  the stores on disk: clients and sessions.

Both come from one command, run on a terminal (it refuses a pipe, so a
secret never lands in a log):

```bash
kyu gen-secret
```

Paste the two lines it prints into `/appdata/kyu/kyu-config/kyu.env`. Without both, a
service with a dashboard refuses to start and `--check` tells you so.

## The dashboard (`dashboard` feature)

A server-rendered set of pages behind the admin login:

| Page | What it is for |
|---|---|
| `/login` | Enter the admin token; a session cookie follows. |
| `/` | The status page: service, health, updates, problems, then the project's own sections. |
| `/clients` | Issue, reveal, copy, re-issue, revoke and delete client tokens; see each client's last requests. |
| project pages | Whatever kyu adds under its own navigation entries. |

The layout, the navigation and the **theme picker** (kp-themes
5.1.0) come from the kit; a chosen theme is remembered by the
browser.

## Health and metrics

`GET /healthz` is open and answers JSON with the running version and one
entry per subsystem. It is HTTP 200 while everything is fine and **503**
as soon as one subsystem reports a failure (`"status":"degraded"`):

```bash
curl -sS http://127.0.0.1:8080/healthz
# {"status":"ok","version":"0.1.0","subsystems":{"store":{"detail":"writable","ok":true}}}
```

`GET /metrics` is open and serves Prometheus text: request counts per
route and status, build info, uptime, and whatever kyu appends.

`kyu --healthcheck` probes `/healthz` of the running instance from
the command line (the container `HEALTHCHECK` and the systemd unit use it)
and exits 0 when a well-formed report came back — degraded still counts
as alive; dead does not.

The project's own numbers go on the same page. `Counter` and `Gauge` from the
kit format the exposition text, so a label value with a quote in it cannot
invalidate the whole scrape — which would take the kit's own metrics with it:

```rust
let delivered = Counter::new(&spec.metric_prefix(), "deliveries_total", "Messages delivered.");
app.metrics_source(delivered.clone());
delivered.inc(&[("topic", "alerts")]);
```

## Self-update (`self-update` feature)

The service can fetch its own next release, verify it and swap the binary
in place. `KYU_UPDATE_MODE` picks who pulls the trigger:

- `off` (default): the status page shows whether a newer release exists;
  nothing is installed.
- `supervised`: the homelab runs `kyu update` on its schedule. That
  one run verifies, installs and exits **0 whether or not anything
  changed** (`already current` is a success); it never restarts the
  service — the supervisor does, after `installed …`.
- `autonomous`: the running process checks on a timer, installs, exits 0
  and lets `Restart=always` start the new binary; a version that does not
  come up healthy is rolled back to the previous binary.

Every release is verified against the **signing key baked into the
binary** before a single byte of it is trusted: the manifest's signature
first, then the binary's SHA-256 against that manifest. A release that
does not verify is refused with nothing installed.

`KYU_UPDATE_HOLD` pins a version (`1.4.0`) or skips one
(`skip:1.4.0`); `KYU_UPDATE_DRILL` is for the broken-release
drill only. Before an update the kit keeps a copy of the state under
`/appdata/kyu/kyu-config-pre-update/<version>/`.

## Command-line controls

| Command | What it does |
|---|---|
| `kyu --version` | Prints `kyu <version>`; reads nothing else. |
| `kyu --check` | Validates the configuration and the project's own checks; opens no socket; exit 0 or 1. |
| `kyu --print-config` | Every knob with its effective value and where it came from (flag, env, file, default); secrets masked. |
| `kyu --knobs` | The table below, for the version of the kit this binary was built with. |
| `kyu --healthcheck [URL]` | Probes `/healthz` of the running instance; exit 0 when alive. |
| `kyu gen-secret` | Prints a fresh `KYU_TOKEN` and `KYU_SECRET_KEY` (terminal only). |
| `kyu update` | One supervised update attempt; exit 0 when current or installed. |
| `kyu --help` | Every flag, including one per knob. |

## The smoke test the kit ships

`tests/kit_smoke.rs` comes from the kit and `chassis sync` keeps it current:
it starts kyu on a free port with a temporary state directory, logs
in as the admin, issues a client, calls one API route with that client's
token and opens the dashboard. It is the fastest way to see whether a
change broke the kit's own path through this service, and it runs with the
project's own `cargo test`.

Do not edit it; write your own tests beside it. The harness it uses
(`chassis::testing`) is documented in the kit's `docs/TESTING.md`.

## What each feature brings with it

A feature is not only a switch: it pulls in other features, dependencies and
bytes. The chain, so a decision to turn one on can be taken with the cost in
view:

| Feature | Pulls in | What it adds |
|---|---|---|
| `core` | — | configuration, logging, `/healthz`, `/metrics`, shutdown, guards. Always on. |
| `assets` | `core` | the vendored kp-themes tree: stylesheets, scripts and **73 font faces, about 5 MB**, embedded in the binary. |
| `dashboard` | `core`, `assets` | the login page, the KYU admin session, the Clients page and the clients API — **and two mandatory secrets** (see below). |
| `passkeys` | `dashboard`, `assets`, `core` | passkey registration and login; pulls OpenSSL, so a static build would have to vendor it. |
| `self-update` | `core` | the updater, its state and the `update` subcommand; pulls a signature verifier. |
| `notify` | `core` | the webhook notifier and the `[[notify.webhook]]` section. |
| `testing` | `dashboard` (and so `assets`, `core`) | the in-process test harness, for `[dev-dependencies]`. It does not reach the built binary. |

**A feature can make a secret mandatory.**
This binary has `dashboard`, which makes `KYU_TOKEN` and
`KYU_SECRET_KEY` required: without both the service refuses to start,
and because the unit runs `--check` as `ExecStartPre`, systemd reports the
refusal instead of starting. Generate them with `kyu gen-secret` and put
both lines in `/appdata/kyu/kyu-config/kyu.env`.

## Who is calling: `Caller`

Every handler the project writes receives a `Caller`, which answers who sent
this request rather than what kind of thing it is. It has two shapes: the
admin, who logged in on the dashboard or sent the admin token, and a client,
one of the rows on the Clients page. So "Clients" is the name of the thing
that registers, and `Caller::Client` is that thing arriving at a route.

## Where things live

- **State**: `KYU_STATE_DIR`, default `/appdata/kyu/kyu-config`. The
  config file, the sealed stores and the update state all live under
  this one directory; nothing is written anywhere else.
- **Environment file**: `/appdata/kyu/kyu-config/kyu.env`, read by the systemd unit
  (`EnvironmentFile=`). It holds the two secrets and any knob you set as
  an environment variable.
- **Pre-update copies**: `/appdata/kyu/kyu-config-pre-update/`, beside the state
  root, not under it.

Everything specific to kyu — its API, its pages, its own settings
and its deployment history — is in this repository's README and the rest
of `docs/`.
